## 0. 先纠正我自己的错误结论

前一份文档我判定「抖加是纯亏损，净烧 $4.51 且零提升」，建议缩到 $0.10/h 预算试探。
**这个结论是错的。** 三处硬伤：

| 错误 | 实际情况 |
| :--- | :--- |
| 拿**同小时收入**衡量抖加 | 抖加的产出是**拿到智能路由的标**，收益在之后数小时到数天才体现 |
| 对照窗口不可比 | 抖加窗口 04:00–08:00 UTC（北京 12:00–16:00），对照 09:00–11:00 UTC（北京 17:00–19:00），时段本身不同 |
| 没算标的前向价值 | `labeled` 渠道日均赚 192,811 quota（$0.386/渠道/日），而恢复一次标只需 $0.006–0.32 |

真实结论是：**抖加有效，而且投入产出比极高。它之所以看起来在烧钱，是因为
(a) 载荷比必要值大 50 倍，(b) 它在向一个已经坏掉的上游打流量。**

## 1. 实测：流量闸门就是「标」

按渠道均摊近 24 小时的外部请求：

| `smart_routing_status` | 渠道数 | 外部请求 | **请求/渠道** |
| :--- | ---: | ---: | ---: |
| `labeled` | 11 | 651 | **59** |
| `normal`（掉标） | 4 | 422 | 106 ← 见下注 |
| `observing`（未拿标） | 4 | 5 | **1.25** |

`labeled` 比 `observing` 高 **47 倍**。

> `normal` 那一行偏高是时间错配：1120 / 1129 在 24 小时窗口的前半段还是 `labeled`
> 并在那时赚到了钱，只是最近才掉标。当前状态是快照，收益是区间累计。

结论：**没有标 = 没有流量。** 这就是你说的「流量根本没跑起来」的机制。

## 3. 实测：上游是坏的，这是根因

13 个 Provider 的当前余额：

| 可用性 | 数量 | 明细 |
| :--- | ---: | :--- |
| ≥ $1（可被 A6 调度） | **2** | m7 $1.65、m2 $1.02 |
| < $1 且 `withdrawable = 0`（无法自救） | **10** | m3 $0.96、m6 $0.79、m9 $0.21、m10 $0.20、m12 $0.20、m15 $0.11、m17 $0.02、m18 $0.01、m11 ~$0、m13 ~$0 |
| < $1 但有钱卡在错池 | 1 | m5：余额 $0.00，可提现 **$0.52 —— 低于 $1 划转下限，动不了** |

**上游池只有 15% 的容量在线。** 每一个落到饿死 Provider 上的请求都会失败 ——
这就是成功率 4%–69% 的来源。

## 4. 死循环

```
        Provider 饿死（13 个只有 2 个 ≥ $1）
                    ↓
        Enodot 上游服务不了请求
                    ↓
        我们的 A6 渠道返回错误 → A6 实测成功率 4%–69%
                    ↓
        爆红爆黄 → cooling → 掉标（labeled → normal / observing）
                    ↓
        智能路由不给流量（labeled 59 次/渠道 vs observing 1.25 次/渠道）
                    ↓
        没有外部收入 → Provider 无法回血
                    ↓
        ────────────── 回到起点 ──────────────
```

**抖加过去在和这个循环搏斗，但它站错了位置，还用了贵 50 倍的弹药。**

历史上抖加确实恢复过标（41 次 `callback_burst` completed），随后真实流量进来，
上游服务不了，成功率崩掉，标又丢 —— 循环重启。钱不是被抖加浪费的，
**是被「向坏掉的上游打流量」浪费的。**

## 5. 关键修正：抖加的载荷贵了 50 倍

| 请求类型 | 事件数 | 平均 prompt tokens | **平均 quota/请求** |
| :--- | ---: | ---: | ---: |
| 抖加（booster token） | 3,248 | **79,809** | **1,894** |
| 普通业务流量 | 4,056 | 49,431 | 483 |
| pin 探活（对照） | 1,085 | 极小 | **~34** |

抖加每次请求发了 **79,809 个 prompt token**。短路请求的目的只是产生一次「成功样本」，
不需要任何真实载荷。

用 pin 探活级别的最小载荷（prompt ~50 token，`max_output_tokens=16`）：

| | 每请求 | 一轮 85 请求 | 降幅 |
| :--- | ---: | ---: | ---: |
| 现状 | 1,894 quota | 160,990 quota = **$0.322** | — |
| 最小载荷 | ~34 quota | 2,890 quota = **$0.006** | **−98%** |

### 5.1 投入产出比

`labeled` 渠道日均赚 192,811 quota = **$0.386/渠道/日**。

| 方案 | 恢复一次标的成本 | 回本时间 |
| :--- | ---: | ---: |
| 现状载荷 | $0.322 | ~20 小时 |
| 最小载荷 | $0.006 | **~21 分钟** |

**即使按现状的贵载荷，只要标能保住，抖加也是正收益。** 它没保住，是因为第 3 节的上游问题。

## 6. 爆发量该是多少：从 100 样本窗口反推

`sample_count` 在所有观测中的上限恰好是 **100**（实测值：100、100、100、67、11、8、5、1、0），
说明 A6 用的是 **100 样本滚动窗口**，`recent_success_rate` 以万分比表示。

要把一个渠道从 4% 拉到 80% 以上（`degraded_success_rate` 阈值是 8000 bp）：

```text
当前 100 样本中约 96 个失败
需要用成功样本挤掉其中 ≥76 个
→ 单轮爆发量 ≈ 85–100 次成功请求
```

**现有 `a6_callback_load.py -c 15 -n 85` 的 85 这个数字是对的** —— 它恰好够翻转一个
100 样本窗口。要改的只有载荷大小，不是请求数。

并发 15 需要按渠道自身限流调整：目标是在窗口内完成，又不触发对方的速率保护。
建议起步 `-c 8`，观察到无 429/限流后再上调。

## 7. 计划

严格按因果顺序。**跳过任何一步，后面的步骤都会把钱烧掉。**

### Stage 0 — 修上游（前置，不可跳过）

抖加向坏上游打流量是唯一能让情况**严格变坏**的动作：付钱买失败，还把成功率压得更低。

| 动作 | 说明 |
| :--- | :--- |
| Provider 收敛到 3 个 | 钱集中，而不是 13 个各锁 $1 全部饿死。走 `trade-assign-roles --apply` |
| 补款到 $2 | `trade-topup-providers-once --floor-units 2`，先 dry-run |
| 处理 m5 类卡死 | 可提现 $0.52 < $1 划转下限，只能等累积；补款命令已正确报 `awaiting_settlement` 而不是把它当故障 |
| 给已退休商户重新上架 | 10 个商户 live listing 为 0，没有收入来源 |

**准入门槛（写进抖加代码）**：目标渠道绑定的 Provider 池中可用（≥ $1）Provider
**少于 2 个时，禁止抖加**。这一条是整个计划的安全阀。

**验收**：连续 2 小时无 `provider_user_balance_below_one_usd`，且我们渠道的 A6 实测
成功率中位数 > 80%。

### Stage 1 — 抖加改最小载荷

| 参数 | 现状 | 目标 |
| :--- | ---: | ---: |
| prompt tokens | 79,809 | ~50 |
| `max_output_tokens` | 未限制（completion 均值 318） | 16 |
| 每请求成本 | 1,894 quota | ~34 quota |

这一步单独就把抖加成本降 98%，把预算从制约因素变成非制约因素。
`--probe-max-output-tokens 16` 已经存在于 pin 服务参数中，抖加复用同一套载荷构造即可。

### Stage 2 — 以「拿标」为成功指标

我上一份文档设计的 `a6_growth_action_outcomes` 指标选错了（用同小时外部收益）。改为：

```sql
-- 真正的成功指标
smart_routing_before   text    -- observing / normal / labeled
smart_routing_after_5m text
smart_routing_after_1h text
success_rate_before    int     -- 万分比
success_rate_after_1h  int
label_acquired         boolean -- observing|normal -> labeled
label_held_seconds     int     -- 标保持了多久才再次丢失
external_earned_24h_after bigint  -- 拿标后 24h 的外部收益（滞后指标）
```

自动开关规则改为：

- **主指标**：`label_acquired` 命中率。连续 10 次爆发命中率 < 30% → 抑制并告警
  （说明上游还没修好，或该渠道被 A6 判定为不可恢复）。
- **次指标**：`label_held_seconds` 中位数。若 < 15 分钟，说明拿标后立刻被真实流量打崩
  → 回到 Stage 0，上游容量不足。
- **不再用同小时收益做判据。**

### Stage 3 — 定价收敛到能赢的区间

近 6 小时按渠道的成功请求数，对照其定价倍率：

| merchant | channel | final 倍率 | ÷ 市场最低价 k | 6h 成功请求 |
| ---: | ---: | ---: | ---: | ---: |
| m2 | 1129 | 0.0096 | 1.6k | **390** |
| m7 | 832 | 0.0245 | 4.1k | 6 |
| m4 | 768 | 0.0128 | 2.1k | 3 |
| m31 | 1289 | 0.300 | **50k** | 4 |
| m21 | 1283 | 0.1033 | 17k | 1 |
| m19 | 1158 | 0.0498 | 8.3k | 0 |
| m5 | 1087 | 0.0172 | 2.9k | 0 |

**流量高度集中在 1.6k 那一档。超过约 2.2k 基本拿不到单。**

现在的 `segmented_log_density_v1` 把 8 个商户从 1.2k 铺到 50k，等于**设计上就让 5–6 个
商户拿不到流量**。这是第三堵墙，而且是我们自己砌的。

改法：

- 把主力压缩到 **1.2k–2.5k**（对应 delta 0.5 → 0.35 区间），6 个商户挤在能赢的窗口内。
- 只留 **1 个**商户在高利润档（比如 8k）作为价格探针，用来测市场上限。
- 价格上限从当前实际的 0.30 提上去这件事**优先级下调** —— 上限不是瓶颈，
  瓶颈是我们把太多商户放在了赢不了的价位。

### Stage 4 — 保标

拿到标之后要守住，否则回到循环。

| 机制 | 触发 | 参数 |
| :--- | :--- | :--- |
| 低频维持抖加 | `sample_count` 中成功样本占比接近 80% 阈值 | 每渠道每小时 ≤ 15 次最小载荷请求 |
| 上下架回收 | `cooling` / `unavailable` | 下架 → `random(0.8, 2.0)s` → 上架；同渠道 ≥10 分钟一次；下架前检查在途请求 |
| 熔断保护 | 上游可用 Provider < 2 | 立刻停止该渠道全部抖加，避免继续买失败 |

### Stage 5 — 扩容

只有当 Stage 0–4 稳定（成功率 > 80%、标保持 > 1 小时、外部收益连续上升）才做：

- Provider 从 3 个按需扩到 `ceil(峰值并发 / 安全并发 / 0.7)`。
- 商户从 8 个扩到 19 个，新商户走 `observing → labeled` 的标准引导流程
  （这正是抖加最高价值的场景：新渠道冷启动）。

## 8. 预算

Stage 1 完成后，抖加成本降到几乎可以忽略，因此预算不应再是主要制约：

| 层级 | 上限 | 依据 |
| :--- | ---: | :--- |
| 单渠道单轮 | 100 请求 ≈ $0.007 | 翻转 100 样本窗口所需 |
| 单渠道每小时 | $0.05 | 允许约 7 轮，足够冷启动 + 维持 |
| 全局每小时 | $0.50 | 19 渠道全量冷启动的上限 |
| 全局每日 | $5.00 | 对照 `labeled` 渠道日均产出 $0.386 × 11 = $4.25，量级匹配 |

上一份文档我建议「从 $0.10/h 起」是基于错误结论的过度保守。按 Stage 1 的成本结构，
$0.50/h 已经能支撑全车队冷启动，且远低于标的产出价值。

**但预算宽松的前提是 Stage 0 的准入门槛生效** —— 上游可用 Provider < 2 时禁止抖加。
没有这个阀门，宽预算只会更快地买失败。
